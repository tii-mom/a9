## 1. 语言选型

| 语言 | 定位 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **Tolk** | TON 官方推荐的新一代合约语言（FunC 的继任者） | 语法更接近现代语言、官方文档与 Acton 工具链主推、静态检查强 | 生态样例比 FunC 少、部分审计方经验较浅 | ✅ 自研合约（RoundController）首选 |
| **FunC** | 老牌合约语言，TON 官方参考合约（Jetton 等）都是 FunC | 参考实现可直接复用、审计经验最多 | 语法晦涩、易出错 | ✅ 官方复用合约保持 FunC 原样，不改写 |
| **Tact** | 高层合约语言（TS 风格） | 开发快、可读性好 | 编译器生成代码面更大、审计需看生成代码 | ⚠️ 备选，不推荐用于资金核心逻辑 |

**推荐组合**：官方 Jetton 用 FunC 原样复用（不改一行）+ 自研 RoundController 用 Tolk 编写。两者通过消息 cell 交互，语言不同不影响互操作。

工具链：Acton（官方推荐的构建/测试/部署工具链）+ 锁定编译器版本 + CI 可重复构建。若审计机构只接受 FunC，则 RoundController 改用 FunC 重写（逻辑不变）。

### 1.1 官方成熟合约覆盖结论（V4）

| 能力 | 官方成熟实现 | 本项目是否采用 | 结论 |
| --- | --- | --- | --- |
| Jetton（TEP-74） | ton-blockchain/jetton-contract | ✅ 采用 | 成熟、可复用；Master + Wallet 原样使用 |
| Multisig v2 | ton-blockchain/multisig-contract-v2 | ❌ 不采用 | 官方有，但**本项目决定不设多签**（营销/流动性个人钱包、管理员单密钥 owner） |
| Lockup / Vesting | ton-blockchain/lockup-wallet-contract | ❌ 不采用 | 官方有，但**团队改为轮次同步释放/销毁**，不需要归属曲线 |
| 轮次状态机 / K 线计数 | 无 | ⚠️ 自研 | 没有官方成熟合约 |
| 成功按质押比例认领 | 无 | ⚠️ 自研 | 没有官方成熟合约（若 D-25 选 pull claim） |
| 失败三笔销毁（奖励 + 团队 + 本金） | 无 | ⚠️ 自研 | 没有官方成熟合约 |
| 团队额度释放 / 销毁 | 无 | ⚠️ 自研 | 没有官方成熟合约 |
| 预言机签名验证（可选） | 无统一标准 | ⚠️ 可选自研 | 二期 OracleAdapter，本期不部署 |

**结论：需要自研的合约数量 = 1（RoundController）；可选 = 1（OracleAdapter，二期）。** 官方复用收敛为 Jetton Master / Wallet 一类。

## 2. 合约清单（要部署几个）

### 2.1 主网目标架构（V4）

| # | 合约 | 来源 | 数量（实例） | 说明 |
| --- | --- | --- | --- | --- |
| 1 | Jetton Master | 官方复用（ton-blockchain/jetton-contract） | 1 | TEP-74，铸造 100 亿、关闭 mint |
| 2 | Jetton Wallet | 官方复用（同上） | N | 每个持币地址 1 个；协议侧约 6 个（奖励金库、质押金库、团队、营销、流动性、运营）+ 用户钱包 |
| 3 | **RoundController** | 自研（Tolk） | 1 | 轮次状态机 + 12 根 K 线计数 + 成功结算（按比例认领 + 团队 1.2 亿释放）+ 失败结算（三笔销毁）+ 领取记账；预计 500~700 行 |
| 4 | Multisig v2 | 官方有，**不采用** | **0** | 项目不设多签（V4） |
| 5 | Lockup / Vesting | 官方有，**不采用** | **0** | 团队改为轮次释放/销毁（V4） |
| 6 | OracleAdapter（可选） | 自研（Tolk，第二阶段） | 0（二期 1） | 签名验证；本期手动模式不部署 |

**部署实例数（V4）**：1（Jetton Master）+ 约 6（协议侧 Jetton Wallet，含团队/营销/流动性个人钱包的 Jetton Wallet）+ 1（RoundController）≈ **8 个**，再加每个用户 1 个 Jetton Wallet。
对比 V3 的约 20 个（含 2 个多签 + 3 个锁仓），V4 因「不设多签、团队轮次释放」显著下降；**真正需要审计的新代码仍只有 1 个合约**。

### 2.2 测试网方案（V4 修订）

V4 撤销 V3 的「多签手动 MVP」（项目不设多签），测试网直接按最终架构执行：

| 步骤 | 执行方 | 链上动作 |
| --- | --- | --- |
| 开轮/关报名 | RoundController（单密钥 owner 触发） | 记录开轮时间、报名截止 |
| 质押 | 用户 | 标准 Jetton transfer 到本轮质押钱包（forward payload 写 roundId/nonce/riskVersion） |
| 提交 K 线 | 任意白名单地址（测试网手动模式） | 提交 12 根 K 线数据（链下公开可复核） |
| 判定/结算 | RoundController | 8/12 判定；成功释放团队额度 + 开放领取；失败发起三笔 burn 并确认后置终态 |
| 开下一轮 | RoundController | 上一轮终态 + 48h 后开启 |

- 测试网阶段自研合约数 = **1（RoundController）**；可选先用单管理员密钥脚本模拟结算（仅测试网、公开标注中心化），但不再使用多签。
- **启动前置（用户明确）**：等所有文档与细节敲定、参数签字后再启动测试网，见 docs/10 §7。

## 4. 自研范围（RoundController）

**只做五件事**：

1. 轮次状态机：UNOPENED → STAKING_OPEN（48h）→ STAKING_CLOSED → OBSERVING（48h / 12 根）→ SETTLING_SUCCESS / SETTLING_FAILURE → SUCCEEDED / FAILED_PERMANENT（含 ORACLE_PAUSED 分支）。
2. K 线记录与计数：仅接受 12 个固定 index、严格时间区间、去重；达标数 >= 8 通过。
3. 成功结算：按质押比例允许领奖（一次性）+ 领回本金；**团队 1.2 亿立即释放**到团队钱包。
4. 失败结算：发出**三笔** burn 指令（奖励 7 亿 + 团队 1.2 亿 + 全部本金），确认后置终态；0 人质押且通过时销毁 7 亿奖励。
5. 领取记账：按（round, owner, type）幂等标记；若 D-25 选方案 B 则包含 pull claim（否则仅记账不做转账）。

**不做**：多签、归属/锁仓（团队轮次同步）、价格聚合（手动/预言机提交）、做市、治理、升级代理。

代码量估计 500~700 行 Tolk + 约 40 个测试用例（成功/失败/无质押/0 人通过/暂停恢复/重复领取/重复销毁/团队释放重复/边界）。

## 5. 审计范围与预算

| 项 | 范围 | 说明 |
| --- | --- | --- |
| 必审 | RoundController（自研） | 资金安全核心：三笔销毁、团队释放、领取、状态机不可逆、0 人质押分支 |
| 必审 | 复用合约的集成方式 | Jetton 转账/销毁、owner 权限、payload 解析 |
| 可选 | OracleAdapter（未来） | 签名验证 |
| 预算 | **$8k~25k**（自研面仅 1 个合约） | 2 周~4 周 |
| 交付 | 审计报告 + 修复复审 + 代码哈希 | 与部署版本一致 |

> 注意：审计覆盖代码逻辑，**不覆盖单密钥托管与个人钱包的运营风险**；该风险已由 V4 接受，缓解见 docs/10 §9。

## 6. 实施顺序（与 docs/10 时间表对齐）

1. **W1**：锁定 Jetton 官方 commit + 审计报告核对；确认「不部署多签/锁仓」的最终参数。
2. **W2**：文档定稿 + 参数签字（含 D-25 奖励领取方式）；Jetton 部署脚本与个人钱包地址登记。
3. **W3~W4**：RoundController（Tolk）实现 + 测试（本地 sandbox + 测试网准备）。
4. **W5**：Testnet 启动（前置：文档定稿 + 参数签字）→ 全流程演练（报名→观察→结算→团队释放/三笔销毁→开下一轮），覆盖无人质押与 0 人通过分支。
5. **W6**：审计 → 修复 → 主网排期。
