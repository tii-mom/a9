## 2. V3 代币经济模型（当前唯一口径）

### 2.1 总量与分配

| 分配 | 占比 | 数量 | 说明 |
| --- | --- | --- | --- |
| 十轮目标解锁奖励（10 × 7 亿） | 70% | 7,000,000,000 | 每轮 7 亿，通过才解锁、失败即销毁 |
| 内盘及流动性 | 13% | 1,300,000,000 | 内盘销售 **3% = 300,000,000**；流动性 **10% = 1,000,000,000** |
| 团队 | 12% | 1,200,000,000 | 每轮 **1.2 亿**，成功即释放、失败即销毁（轮次同步，无 vesting；D-20） |
| 营销推广 | 5% | 500,000,000 | **个人钱包**持有，项目不设多签（D-21，风险接受） |
| **合计** | **100%** | **10,000,000,000** | 校验：7000 + 1300 + 1200 + 500 = 10000（百万） |

### 2.2 价格阶梯

- target(n) = P0 × 2ⁿ（n = 1…10）；第 10 轮 = **1024 × P0**。
- **P0 = $0.001**（USD_E8 = 100,000）→ 第 10 轮目标价 **$1.024**；FDV@P0 = **$10,000,000**。
- 决策依据：本轮目标是「第 10 轮目标价约 1 美元」，因此 P0 由 V2 的 $0.004 下调为 $0.001（1024 × 0.001 = 1.024）。

| 轮次 | 倍率 | 目标价 | 每轮奖励 |
| --- | --- | --- | --- |
| R1 | 2× | $0.002 | 700,000,000 |
| R2 | 4× | $0.004 | 700,000,000 |
| R3 | 8× | $0.008 | 700,000,000 |
| R4 | 16× | $0.016 | 700,000,000 |
| R5 | 32× | $0.032 | 700,000,000 |
| R6 | 64× | $0.064 | 700,000,000 |
| R7 | 128× | $0.128 | 700,000,000 |
| R8 | 256× | $0.256 | 700,000,000 |
| R9 | 512× | $0.512 | 700,000,000 |
| R10 | 1024× | $1.024 | 700,000,000 |
| **合计** | — | — | **7,000,000,000** |

轮次不因失败回滚；失败轮永久关闭。

### 2.3 每轮机制

1. **报名（48 小时）**：用户把 A9 转入质押金库，payload 写入风险确认（roundId / nonce / riskDisclosureVersion / acceptFullPrincipalBurn=true）。上一轮结算完成后 48 小时开启，报名关闭即进入观察。
2. **观察（48 小时）**：12 根连续 4 小时 K 线，每根用多源 TWAP（≥8 根 ≥ 目标价即通过，等于也算）。
3. **成功**：本金退还 + **7 亿奖励按质押比例认领**（领取方式 D-25 待定，推荐 pull claim）+ **团队 1.2 亿立即释放到团队钱包**（无 cliff、无线性）。
4. **失败**：三笔销毁 —— 本轮 **7 亿奖励 + 团队轮次额度 1.2 亿 + 本轮全部质押本金**；供应量减少，失败轮永久关闭。
5. **无人质押**：本轮照常启动并进入观察（不卡轮次、不判负）。
   - 失败：照常销毁本轮奖励（无本金可销毁）。
   - 通过：本轮奖励按质押比例分给所有质押人；即使只有 1 人，该人拿走本轮全部奖励。
   - 0 人质押且通过：奖励无接收人 → **本轮 7 亿奖励销毁**（D-18b 已确认：不回流、不留存、不补发）。

### 2.4 隐含估值

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| P0 对应 FDV | 100 亿 × $0.001 | **$10,000,000** |
| 十轮全通过后 FDV | 100 亿 × $1.024 | **$10,240,000,000** |
| 十轮全通过市值放大 | 1024 × P0 | **1024 倍** |

> V2 历史：当时演示 P0 = $0.004 → R10 = $4.096、FDV@P0 = $40,000,000；V3 已按「R10 ≈ $1」下调 P0 至 $0.001，该旧数字仅作历史记录，不再作为口径。

### 2.5 团队额度释放 / 销毁（V4）

团队 12% = 1,200,000,000 与轮次**完全同步**，每轮：

``` text
TEAM_ROUND_RAW = 1,200,000,000 / 10 = 120,000,000（1.2 亿）
托管：12 亿全部存放在 RoundController 持有的 Jetton Wallet（owner = RoundController）
本轮 SUCCEEDED        → 1.2 亿立即转出到团队个人收款钱包（无 cliff / 无线性）
本轮 FAILED_PERMANENT → 1.2 亿销毁（burn_ledger kind = "team"）
```

- 团队额度必须由**控制器托管**（而非一开始就放个人钱包），否则控制器无权在失败轮销毁该额度。
- 不部署 Lockup / Vesting 合约，团队没有独立归属曲线；原「12 个月 cliff + 36 个月线性」描述**作废**。
- 释放与销毁互斥，每轮最多一次。
- 供应量：成功轮不减少供应（只是从团队额度转为流通）；失败轮 total_supply 实际减少 1.2 亿。

### 2.6 托管与权限（V4：不设多签）

- **营销 5%（5 亿）与流动性 10%（10 亿）放入个人钱包**，项目不部署多签合约。
- 管理员权限为 **RoundController 单密钥 owner**，权限最小化：不能转移用户质押本金、不能修改已开轮的目标价 / 阈值 / oracle 配置；紧急暂停不得改变价格判定结果。
- 风险接受：单私钥丢失 / 泄露即失去对应资金与管理员能力。缓解要求：硬件钱包、冷热分离、地址公开、密钥备份与轮换演练、控制器不可升级（详见 docs/10 §9）。
- 不部署 Multisig v2；调用方不能假设存在多签治理或时间锁。

### 2.7 销毁口径（V4：三笔）

失败轮次销毁量：

``` text
burnAmount = ROUND_REWARD（7 亿）+ TEAM_ROUND（1.2 亿）+ totalAcceptedStake
```

示例（演示 R2）：700,000,000 + 120,000,000 + 241,500,000 = **1,061,500,000 A9**。
burn_ledger 按三笔记录：kind = `reward` / `team` / `principal`，各自唯一 burnId 与确认状态。

## 5. 合约来源策略（优先复用官方/已审计）

原则：**能复用就不自研；自研部分只保留无法避免的状态机，并单独审计。**

| 模块 | 建议来源 | 复用程度 | 需核对 |
| --- | --- | --- | --- |
| Jetton Master / Wallet | TON 官方参考实现（ton-blockchain/jetton-contract，TEP-74） | 直接复用 | 固定 commit + 编译版本；确认 mint 权限可关闭；核对第三方审计报告覆盖的版本 |
| 奖励金库 | **标准 Jetton Wallet（owner = RoundController）**（不写合约） | 直接复用 | 持有 **70 亿**，按轮次记账在控制器/链下；每轮 **7 亿** |
| 质押金库 | 标准 Jetton Wallet（owner = RoundController） + forward payload 记账 | 复用为主 | 需要控制器解析 payload |
| 团队额度 | 标准 Jetton Wallet（owner = RoundController），**控制器托管** | 复用为主 | 12 亿，按轮次转出 1.2 亿到团队收款钱包 / 失败销毁 1.2 亿 |
| 营销 / 流动性 | **个人钱包（非合约）**，不部署 Lockup / Multisig | 不适用 | 5% / 10% 个人钱包持有（风险接受） |
| RoundController / 判定 | **自研（唯一必须自研）** | 自研 | 状态机 + K 线计数 + 结算指令 + 领取记账，代码量控制在 500~700 行内 |
| 预言机 | **本期不接入**；保留 OracleAdapter 接口与配置字段 | 预留（可选自研） | 主网前必须恢复签名验证 |

**官方覆盖结论（V4）**：Jetton（TEP-74）有官方成熟实现，直接复用；Multisig v2 官方有但**本项目不用**；Lockup/Vesting 官方有但**团队改为轮次释放，不需要**；轮次状态机 / K 线计数 / 按比例认领 / 失败销毁 / 团队额度释放销毁**没有官方成熟合约**，必须自研 RoundController（1 个）。

**测试网启动前置**：用户明确「等所有文档和细节敲定后再启动测试网」。测试网按最终架构执行（RoundController 自研 1 个，不再走多签手动 MVP），启动时点见 docs/10 §7。
