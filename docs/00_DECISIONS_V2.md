## 2. 代币经济模型（V5 当前口径）

### 2.1 总量与分配

| 分配 | 占比 | 数量 | 说明 |
| --- | --- | --- | --- |
| 十轮目标解锁奖励（10 × 7 亿） | 70% | 7,000,000,000 | 每轮 7 亿，通过才解锁、失败即销毁 |
| 内盘及流动性 | 13% | 1,300,000,000 | 内盘销售 **3% = 300,000,000**；流动性 **10% = 1,000,000,000** |
| 团队 | 12% | 1,200,000,000 | 每轮 **1.2 亿**，成功即释放、失败即销毁（轮次同步，无 vesting；D-20） |
| 营销推广 | 5% | 500,000,000 | **个人钱包**持有，项目不设多签（D-21，风险接受） |
| **合计** | **100%** | **10,000,000,000** | 校验：7000 + 1300 + 1200 + 500 = 10000（百万） |

### 2.2 价格阶梯

- target(n) = P0 × 2ⁿ（n = 1…10）；第 10 轮 = **1024 × P0**。
- **P0 = $0.001**（USD_E8 = 100,000）→ 第 10 轮目标价 **$1.024**；FDV@P0 = **$10,000,000**。
- 决策依据：本轮目标是「第 10 轮目标价约 1 美元」，因此 P0 由 V2 的 $0.004 下调为 $0.001（1024 × 0.001 = 1.024）。

| 轮次 | 倍率 | 目标价 | 每轮奖励 |
| --- | --- | --- | --- |
| R1 | 2× | $0.002 | 700,000,000 |
| R2 | 4× | $0.004 | 700,000,000 |
| R3 | 8× | $0.008 | 700,000,000 |
| R4 | 16× | $0.016 | 700,000,000 |
| R5 | 32× | $0.032 | 700,000,000 |
| R6 | 64× | $0.064 | 700,000,000 |
| R7 | 128× | $0.128 | 700,000,000 |
| R8 | 256× | $0.256 | 700,000,000 |
| R9 | 512× | $0.512 | 700,000,000 |
| R10 | 1024× | $1.024 | 700,000,000 |
| **合计** | — | — | **7,000,000,000** |

轮次不因失败回滚；失败轮永久关闭。

### 2.3 每轮机制

1. **报名（72 小时）**：用户把 A9 转入质押金库，payload 写入风险确认（roundId / nonce / riskDisclosureVersion / acceptFullPrincipalBurn=true）。上一轮结算后**立即开启**，窗口 72 小时，报名关闭即进入观察。
2. **观察（48 小时）**：12 根连续 4 小时 K 线，每根用多源 TWAP（≥8 根 ≥ 目标价即通过，等于也算）。
3. **成功**：本金退还 + **7 亿奖励按质押比例认领**（pull claim，可跨轮累积一次性领取）+ **团队 1.2 亿由 TeamVault 立即转出到团队收款钱包**（无 cliff、无线性）。
4. **失败**：三笔销毁 —— 本轮 **7 亿奖励 + 团队轮次额度 1.2 亿 + 本轮全部质押本金**；供应量减少，失败轮永久关闭。
5. **无人质押**：本轮照常启动并进入观察（不卡轮次、不判负）。
   - 失败：照常销毁本轮奖励（无本金可销毁）。
   - 通过：本轮奖励按质押比例分给所有质押人；即使只有 1 人，该人拿走本轮全部奖励。
   - 0 人质押且通过：奖励无接收人 → **本轮 7 亿奖励销毁**（D-18b 已确认：不回流、不留存、不补发）。

### 2.4 隐含估值

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| P0 对应 FDV | 100 亿 × $0.001 | **$10,000,000** |
| 十轮全通过后 FDV | 100 亿 × $1.024 | **$10,240,000,000** |
| 十轮全通过市值放大 | 1024 × P0 | **1024 倍** |

> V2 历史：当时演示 P0 = $0.004 → R10 = $4.096、FDV@P0 = $40,000,000；V3 已按「R10 ≈ $1」下调 P0 至 $0.001，该旧数字仅作历史记录，不再作为口径。

### 2.5 团队额度与 TeamVault（V5）

团队 12% = 1,200,000,000 由**独立 TeamVault 合约**托管，与轮次**完全同步**：

``` text
TEAM_ROUND_RAW = 1,200,000,000 / 10 = 120,000,000（1.2 亿）
托管：TeamVault 持有 12 亿对应的 Jetton Wallet（owner = TeamVault 合约）
每轮结算：RoundController → TeamVault 发指令
  本轮 SUCCEEDED        → TeamVault 转 1.2 亿到团队收款钱包（无 cliff / 无线性）
  本轮 FAILED_PERMANENT → TeamVault 销毁 1.2 亿（burn_ledger kind = "team"）
```

- **TeamVault 只接受 RoundController 的指令**；其他来源的消息一律拒绝。
- 同一轮释放与销毁**互斥**、**幂等**（每轮最多一次，重复指令返回已有结果）。
- 团队收款钱包地址在**部署前填入 config**（热钱包，见 §2.6）。
- 不部署 Lockup / Vesting 合约，团队没有独立归属曲线；原「12 个月 cliff + 36 个月线性」描述**作废**。
- 供应量：成功轮不减少供应（额度转为流通）；失败轮 total_supply 实际减少 1.2 亿。

### 2.6 托管与权限（V5：不设多签，单密钥最小权限）

- **不设多签**；营销 5%（5 亿）与流动性 10%（10 亿）由**个人热钱包**持有；团队收款钱包同样是热钱包。
- **收款钱包地址不对外披露**：由项目方在部署前提供，填入部署 config；公开材料只说明"由项目方热钱包持有"，具体地址至少向审计方/交易所披露（见 docs/10 §9）。
- **管理员 = RoundController 单密钥 owner**，**仅**保留最小权限：开轮、关报名、暂停/恢复预言机、必要时触发结算；不得修改已开轮的目标价 / K 线阈值 / 预言机配置，不得转移用户质押本金。
- **RoundController 不可升级**（D-24 已确认，无升级代理），管理员无法通过升级改变规则。
- 风险接受：单私钥丢失 / 泄露即失去对应资金或管理员能力；缓解要求见 docs/10 §9（硬件钱包、冷热分离、私钥备份、至少向审计/交易所披露、密钥轮换演练）。

### 2.7 销毁口径（V4：三笔）

失败轮次销毁量：

``` text
burnAmount = ROUND_REWARD（7 亿）+ TEAM_ROUND（1.2 亿）+ totalAcceptedStake
```

示例（演示 R2）：700,000,000 + 120,000,000 + 241,500,000 = **1,061,500,000 A9**。
burn_ledger 按三笔记录：kind = `reward` / `team` / `principal`，各自唯一 burnId 与确认状态。团队这一笔由 TeamVault 执行（见 §2.5）。

## 5. 合约来源策略（优先复用官方/已审计）

原则：**能复用就不自研；自研部分只保留无法避免的状态机，并单独审计。**

| 模块 | 建议来源 | 复用程度 | 需核对 |
| --- | --- | --- | --- |
| Jetton Master / Wallet | TON 官方参考实现（ton-blockchain/jetton-contract，TEP-74） | 直接复用 | 固定 commit + 编译版本；确认 mint 权限可关闭；核对第三方审计报告覆盖的版本 |
| 奖励金库 | **标准 Jetton Wallet（owner = RoundController）**（不写合约） | 直接复用 | 持有 **70 亿**，按轮次记账在控制器/链下；每轮 **7 亿** |
| 质押金库 | 标准 Jetton Wallet（owner = RoundController） + forward payload 记账 | 复用为主 | 需要控制器解析 payload |
| **TeamVault（团队金库）** | **自研（V5 新增）** | 自研 | 托管 12 亿 Jetton Wallet（owner = TeamVault）；只接受 RoundController 指令，按轮转出/销毁 1.2 亿，幂等互斥；约 150~250 行 |
| 营销 / 流动性 | **个人热钱包（非合约）**，不部署 Lockup / Multisig | 不适用 | 5% / 10% 热钱包持有，地址不对外披露（风险接受） |
| RoundController / 判定 / 领取 | **自研（2 个之一）** | 自研 | 状态机 + K 线计数 + 结算指令 + 团队指令 + claimAll（≤10 轮有界），代码量控制在 500~700 行内 |
| 预言机 | **本期不接入**；保留 OracleAdapter 接口与配置字段 | 预留（可选自研） | 主网前必须恢复签名验证 |

**官方覆盖结论（V5）**：Jetton（TEP-74）有官方成熟实现，直接复用；Multisig v2 官方有但**本项目不用**；Lockup/Vesting 官方有但**团队由 TeamVault 轮次释放，不需要**；轮次状态机 / K 线计数 / 按比例认领（claimAll）/ 三笔销毁 / 团队额度释放销毁**没有官方成熟合约**，必须自研 **RoundController + TeamVault（2 个）**。

## 7. V5 解锁窗口与目标价冲突（待决策）

> **状态：待决策，尚未定案。** 本节三个方案均未生效，**不要按其中任何方案进入合约设计或改参数**；当前仍按固定阶梯 `P0 × 2^n` 运行。

### 7.1 问题

第 4 轮 72 小时报名期内，若现价已 ≥ 第 4 轮目标价，则结果基本确定（观察期只要不大跌就通过）：参与者在报名时已经知道会赢，等于**无风险白拿 7 亿奖励**，奖励被逐轮抛售，机制失效。
报名窗口越长（V5 已改为 72h）、后段阶梯越平（固定 P0×2^n 相对现价越来越低），该问题越明显。

### 7.2 方案 A（Lead 推荐）：目标价改为相对翻倍

- 每轮**报名截止时锁定**目标价：`targetPrice = 2 × 报名期参考 TWAP`。
- 参考窗口建议取**最后 24 小时**（覆盖率/来源数阈值另定）。
- 连赢 10 轮仍是 **1024 倍**，每轮翻倍语义不变；价格提前超过旧阶梯也不会白拿，因为目标价随之上移。
- `P0 × 2^n` 退化为**早期轮次的参考**，不再作为全程固定目标。
- 待定参数：参考 TWAP 窗口长度、覆盖率与来源阈值、锁定后是否允许变更、报名期数据不足时的回退规则。

### 7.3 方案 B：保留固定阶梯 + 开窗价格闸门

- 仅当**现价低于目标价的 95%** 才开报名；否则等待（最长 7 天）；超时则**顺延到下一阶**（跳过本轮，不销毁）。
- 缺点：可能长期空转；状态机更复杂（新增等待态/跳过态）；95% 阈值本身也可能被操纵。

### 7.4 方案 C：保留固定阶梯 + 缩短窗口 + 随机截止

- 报名窗口缩到 24~48h，截止时间随机化，配合 commit-reveal 降低狙击。
- 只能**缓解**、不能根治：若价格已明显高于目标价，短窗口仍然白拿。

### 7.5 三个方案的共同前提

- **价格输入必须可信**：测试网为手动提交（可伪造，仅测试）；主网必须接入预言机/签名数据源，否则方案 A 的参考价与方案 B 的闸门都失去意义。
- 任一方案都会影响 `RoundData.targetPriceUsdE8` 的计算时点、K 线判定语义、前端倒计时与文案；选定后需同步修改 docs/01、02、04、09、11 与合约参数。

### 7.6 当前结论

等待项目方选择 A / B / C；选定后再改合约设计与参数。当前配置 `targetMode = FIXED_LADDER`（`RELATIVE_DOUBLE` 仅作为预留开关，未启用）。
