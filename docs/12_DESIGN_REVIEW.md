# 12 — 设计评审：闭环检查与优化清单

**版本**：V1.0 · 2026-11-05
**范围**：docs/00~11、现有合约设计（RoundController + TeamVault + Jetton 复用）、前端与后端实现。
**结论**：机制主体已经闭环（发行 → 质押 → 判定 → 结算 → 销毁/释放 → 下一轮），但仍有 **6 个 P0 级缺口**、**7 个 P1 级优化**、**若干 P2 打磨项**。P0 不解决，不建议上主网。

---

## 1. 闭环检查

| 维度 | 是否闭环 | 说明 |
| --- | --- | --- |
| 代币发行 | ✅ | 100 亿总量、70/13/12/5 分配、mint 关闭 |
| 质押 → 判定 → 结算 | ✅ 基本闭环 | 12/48h/8 已定；B+ 闸门/触价关窗待定 |

## 2. P0 级缺口（上主网前必须解决）

### P0-1 首轮目标价怎么定（启动问题）
**问题**：P0 是初始参考价，R1 目标 = 2×P0。但 TGE 时价格 ≈ P0，首轮就要求 48h+72h 内翻倍，几乎必然失败；首轮失败 = 全部质押本金销毁 + 7 亿 + 1.2 亿销毁，项目开局即崩。
**建议**：R1 作为「启动轮」特殊处理，三选一：
- A. R1 目标 = 1.3~1.5 × 上市基准 TWAP（之后每轮 ×2）；
- B. R1 目标 = 2×P0，但报名期给 7 天 + 上线预热（用时间换空间）；
- C. R1 不设目标、不销毁（空跑一轮做启动宣传），R2 起进入正式机制。
**推荐 A**：最符合「首轮要赢」的运营目标，且不破坏后续阶梯。

### P0-2 经济模型未验证（EV / 蒙特卡洛）
**问题**：目标 48h 内翻倍，观察期 12 根中 8 根达标；在常见波动率下通过概率可能只有 20~35%。失败损失 100% 本金，成功收益 = 7 亿 ÷ 本轮质押。若质押池大，奖励回报可能远低于本金风险 → 玩家期望为负 → 无人参与。
**建议**：主网前用蒙特卡洛模拟（几何布朗运动 + 不同波动率/质押池规模）跑出：通过概率、EV、最优质押池、奖励倍数区间；据此调 P0、倍率、观察窗口。**没有这份数据就上主网 = 赌博。**

### P0-3 预言机/价格来源未定
**问题**：B+ 的闸门、触价关窗、判定都依赖可信价格。测试网手动提交可以，但主网必须签名验证。
**建议**：主网前完成 3/5 独立签名方 + 24h/1h TWAP + 覆盖率/偏差过滤，并冻结 oracle config hash。

### P0-4 法律意见书
**问题**：100% 本金销毁 + 逐轮翻倍的机制，在多数辖区可能被认定为博彩/金融产品。
**建议**：主网前取得书面法律意见，明确辖区限制、KYC/AML 要求、风险披露文本版本。

### P0-5 首轮与失败轮的目标语义（同档重试）
**问题**：当前「失败后进入下一阶」（R3 失败 → R4 目标 4×P0 的下一阶 8×P0）在价格下跌时会连续失败、连续销毁，10 轮很快烧完。
**建议**：改为 **「成功升档、失败同档重试」**：R3 目标 $0.008 失败 → R4 仍是 $0.008；只有成功才进入 $0.016。这样每轮都要求「从当前价再涨到同一目标」，可达性大幅提高。
**连带影响**：10 轮不再等于 10 个档位（失败会占用轮次），前端阶梯要从「轮次」改为「档位」展示，需要一次 UI 重构。

### P0-6 技术终止与暂停的兜底
**问题**：管理员单密钥可暂停；若私钥丢失或长期不恢复，资金永久锁死。
**建议**：合约内置「暂停超过 14 天 → 任何人可触发 TECHNICAL_ABORTED 并退还本金」的时间锁逻辑（不需要多签），把单点风险降到可控。

## 3. P1 级优化

| # | 问题 | 建议 |
| --- | --- | --- |
| P1-1 | 团队额度成功即释放，可能被立即抛售 | 释放后加 7 天线性/延迟，或公开团队地址与用途 |
| P1-2 | 营销/流动性在个人热钱包，无多签 | 至少硬件钱包 + 冷热分离 + LP 锁定 + 地址对审计披露 |
| P1-3 | 最后几小时搭便车（临近目标价进场） | 两档时间权重（前 24h 1.0×，后 48h 0.5×），或先观察数据再上 |
| P1-4 | 10 轮结束后协议无后续 | 定义 R10 后状态：代币用途、剩余金库、是否进入二级市场治理 |
| P1-5 | 价格闸门的 TWAP 计算方未定义 | 明确「谁算 1h TWAP、数据源、覆盖率、偏差阈值」 |
| P1-6 | 参数分散在文档各处 | 建立唯一参数表 + 配置哈希，部署脚本从该表生成 |
| P1-7 | 审计只覆盖合约，不覆盖经济与前端 | 增加经济模型审计 + 前端密钥/钓鱼风险检查 |

## 4. P2 打磨

- 前端阶梯改「档位」视图（同档重试后必须改）；
- 增加「等待价格条件」状态页与倒计时分享卡片；
- 后台增加 TeamVault 释放/销毁状态、claimAll 统计、对账差异告警；
- D1 每日备份到 R2、密钥轮换演练；
- 公开「销毁证明」页（burn 交易哈希 + total_supply 变化）；
- 英文文案与法律声明同步。

---

## 5. 优先级建议（按周）

1. **第 1 周**：确认 R1 启动规则、同档重试、搭便车方案；写参数表；
2. **第 2 周**：蒙特卡洛模拟 + 参数调优（P0-2）；法律意见启动；
3. **第 3~4 周**：RoundController + TeamVault 实现（含技术终止超时）；
4. **第 5 周**：Testnet 全流程演练（成功/失败/无人质押/暂停恢复/技术终止）；
5. **第 6 周**：审计 + 修复；前端接测试网；
6. **第 7 周**：主网参数冻结、部署、R1 启动。

---

## 6. 结论

**机制主体闭环，但还不能称为「完美」**：最大的三个洞是「首轮必败」「经济未验证」「失败后目标不可达」，这三个都会直接导致项目开局失败。建议先把这三项定下来，再进入合约实现——否则合约写完还要返工。
